Database Foundations

Deep first principles of relational databases: how data is stored, organized, retrieved, and protected. Every senior engineer must own this layer completely.

Chapter 1

Relational Databases & Schema Design

How relational databases are structured, how schema decisions compound into production pain, and how staff engineers think about data modeling.

1.1 What is a Relational Database, Really?

A relational database is not just a spreadsheet in a server. It is a mathematical model rooted in Edgar Codd's 1970 relational algebra. The core idea: data is organized into relations (tables), each with a defined schema (columns with types and constraints), and rows (tuples) represent individual records conforming to that schema.

What makes it powerful is the query engine: you express what you want (declarative SQL), and the database engine figures out how to execute it — choosing join algorithms, index access paths, and execution order via its query optimizer. This separation is what makes SQL so expressive and databases so powerful for correctness.

The Relational Model Core Primitives

Relation (Table): A set of tuples (rows), each conforming to the same attribute schema.

Primary Key: A column or minimal set of columns that uniquely identifies each row. Enforces entity integrity.

Foreign Key: A reference from one relation to a primary key in another, enforcing referential integrity.

Constraints: Rules that the engine enforces (NOT NULL, UNIQUE, CHECK, DEFAULT) — your data contract.

1.2 Schema Design: The Decisions That Haunt You at Scale

Schema design is the most consequential decision in any backend system. Bad schemas cause query slowness, data integrity bugs, migration nightmares, and impossible-to-fix architectural debt years later. Staff engineers treat schema changes with the same rigor as API contract changes.

The Classic SaaS Multi-Tenant Schema
-- Production-grade multi-tenant SaaS schema
CREATE TABLE organizations (
  id          BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  slug        VARCHAR(100) NOT NULL,
  name        VARCHAR(255) NOT NULL,
  plan        ENUM('free', 'pro', 'enterprise') NOT NULL DEFAULT 'free',
  created_at  DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  PRIMARY KEY (id),
  UNIQUE KEY uq_org_slug (slug)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

CREATE TABLE users (
  id              BIGINT UNSIGNED NOT NULL AUTO_INCREMENT,
  organization_id BIGINT UNSIGNED NOT NULL,
  email           VARCHAR(320) NOT NULL,
  password_hash   VARCHAR(255) NOT NULL,
  role            ENUM('owner', 'admin', 'member') NOT NULL DEFAULT 'member',
  status          ENUM('active', 'suspended', 'deleted') NOT NULL DEFAULT 'active',
  created_at      DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6),
  updated_at      DATETIME(6) NOT NULL DEFAULT CURRENT_TIMESTAMP(6) ON UPDATE CURRENT_TIMESTAMP(6),
  deleted_at      DATETIME(6) NULL,  -- soft delete
  PRIMARY KEY (id),
  UNIQUE KEY uq_user_email_org (organization_id, email),
  KEY idx_user_org (organization_id),
  CONSTRAINT fk_user_org FOREIGN KEY (organization_id) REFERENCES organizations (id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;
Senior Engineer Observations on This Schema

BIGINT UNSIGNED: Always use BIGINT (not INT) for primary keys in systems that will grow. INT gives you 2.1 billion rows max — a SaaS hitting 10M users with activity logs will overflow INT PKs in months.

DATETIME(6): The (6) gives microsecond precision. Always use this for created_at/updated_at — you will thank yourself when debugging race conditions at millisecond granularity.

Soft deletes (deleted_at): Never hard-delete user data in SaaS. Audit, GDPR, and undo-delete requirements will come. Every index on this table must be aware of deleted_at IS NULL.

utf8mb4: Always. Never use utf8 in MySQL — it's a broken 3-byte encoding that can't store emoji or certain Chinese characters. utf8mb4 is the real UTF-8.

Common Mistakes That Cause Production Pain

Storing money as FLOAT/DOUBLE: Floating point arithmetic is inexact. $10.10 stored as FLOAT may become $10.0999999... Use DECIMAL(19,4) or store amounts in the smallest currency unit (cents as INT).

Using VARCHAR(255) for everything: MySQL uses VARCHAR column length to size internal sort buffers. 100 VARCHAR(255) columns means 25KB per row for sorting — your filesort operations will be 10x slower than necessary.

Not indexing foreign keys: MySQL does NOT automatically create indexes on foreign key columns (unlike PostgreSQL). Every unindexed FK causes full table scans on child tables during JOIN and cascade operations.

1.3 The Mental Model for Schema Design

Staff Engineer Mental Model: Schema as API Contract

Treat your schema like a public API. Once rows exist in production, every column, type, and constraint is a contract with your data. Changing types requires migration + backfill. Removing columns requires coordinating app deploys. Adding NOT NULL to existing columns requires defaults or backfills.

Design schema for the queries you need to run, not just for the data you want to store. Start from your most critical query patterns, then design the schema + indexes around them.

Chapter 2

Normalization vs. Denormalization

The foundational tradeoff of database design — and why senior engineers constantly navigate the spectrum between these two poles based on access patterns.

2.1 Normalization: Eliminating Redundancy

Normalization is the process of structuring a database to reduce data redundancy and improve integrity. It was formalized by Edgar Codd through a series of "normal forms" — each building on the last.

Normal FormWhat it EliminatesRule
1NFRepeating groups, multi-valued columnsEach column contains atomic (indivisible) values; each row is unique
2NFPartial dependenciesEvery non-key column depends on the WHOLE primary key (no partial dependency on composite keys)
3NFTransitive dependenciesEvery non-key column depends ONLY on the primary key, not on other non-key columns
BCNFRemaining anomaliesEvery determinant is a candidate key
Violation Example and Fix
-- VIOLATION: Transitive dependency (3NF violation)
-- zip_code → city, state (city depends on zip, not on user_id)
orders (user_id, zip_code, city, state, amount)

-- FIXED: Normalized
orders (user_id, zip_code, amount)
zip_codes (zip_code, city, state)   -- separate lookup table

2.2 Denormalization: Trading Integrity for Performance

At scale, normalized schemas often require complex multi-table JOINs for every query. Each JOIN has a cost: disk reads, memory usage, CPU for hash/merge operations. Denormalization intentionally introduces redundancy to eliminate JOINs on hot read paths.

Real Production Denormalization Example

An e-commerce order page needs: order info + user name + product names + category names. Normalized: 5-table JOIN on every page load. At 50K orders/day this becomes unacceptable.

Solution: Snapshot critical data at write time. Store user_name, product_snapshot JSON directly on the order row. Accept that if a user changes their name, old orders show the old name — which is actually correct behavior for order history.

Common Denormalization Patterns
Denormalization WIN
  • Materialized counts: Store comment_count on posts table — avoid COUNT(*) query
  • Precomputed aggregates: Store daily totals in a separate rollup table
  • Snapshot at write: Store price/name at order time — correct + fast reads
  • Embedding in JSON: Store tags as JSON array when filtering by individual tags is rare
Denormalization DANGER
  • Duplicating data that updates frequently — synchronization complexity
  • Storing computed values that need to be consistent — cache invalidation hell
  • Premature denormalization without profiling the actual bottleneck
  • Denormalizing fields used in WHERE clauses — now you must update both places
Mental Model: Normalize for Writes, Denormalize for Reads

Start fully normalized. Profile your slowest queries. Identify which JOINs are costly. Selectively denormalize those specific paths. This is the CQRS (Command Query Responsibility Segregation) principle applied at the database level.

Chapter 3

Indexing Deep Dive

Indexes are the single most impactful performance lever in any database. Most engineers use them; few truly understand their internals, costs, and failure modes.

3.1 What an Index Actually Is

An index is a separate data structure maintained by the database engine that allows rows to be found without scanning every row in the table. In MySQL InnoDB, the primary key is stored as a B+Tree where leaf nodes contain the actual row data (clustered index). Secondary indexes are separate B+Trees where leaf nodes contain the primary key value.

B+Tree Index Structure (Simplified) [Root: 50] / \ [25 | 37] [75 | 87] / | \ / | \ [1..24] [25..36] [37..49] [50..74] [75..86] [87..N] | | | Leaf nodes contain: [key | row_data (clustered) OR primary_key (secondary)] Leaf nodes are linked as a doubly-linked list → efficient range scans Height of tree ≈ log₃(N rows) → 3-4 levels for 1 billion rows Each level = 1 disk I/O = 4-8ms on HDD, ~0.1ms on NVMe SSD

3.2 Index Types in MySQL

Index TypeUse CaseInternals
PRIMARY KEYClustered — physical row orderB+Tree; leaf nodes ARE the rows
UNIQUEEnforce uniqueness + fast lookupB+Tree secondary index
INDEX (KEY)Speed up queries on non-unique columnsB+Tree secondary index; stores PK in leaf
FULLTEXTText search across multiple columnsInverted index (word → row mapping)
CompositeFilter/sort on multiple columnsB+Tree on (col1, col2, ...) combined key
PrefixIndex on first N chars of VARCHARReduces index size; can't use for ORDER BY

3.3 The Most Important Rule: Composite Index Column Order

Composite indexes follow the leftmost prefix rule. An index on (a, b, c) can be used for queries on (a), (a, b), or (a, b, c) — but NOT on (b) or (b, c) alone. The engine walks the B+Tree from the leftmost key.

-- Index on (organization_id, status, created_at)
CREATE INDEX idx_orders_org_status_date
  ON orders (organization_id, status, created_at);

-- ✅ Uses full index (leftmost prefix fully matched)
SELECT * FROM orders
WHERE organization_id = 5
  AND status = 'pending'
  AND created_at > '2024-01-01';

-- ✅ Uses partial index (stops after status)
SELECT * FROM orders
WHERE organization_id = 5
  AND status = 'pending';

-- ❌ Cannot use index efficiently (skips organization_id)
SELECT * FROM orders
WHERE status = 'pending'
  AND created_at > '2024-01-01';

3.4 Covering Indexes: The Performance Superweapon

A covering index is one where the index contains ALL columns needed by the query. The engine never touches the actual table rows — it satisfies the entire query from the index B+Tree. This eliminates the second random I/O (the "bookmark lookup") and can be 5–100x faster for certain queries.

-- Query needs: user_id filter, returns email + created_at
SELECT email, created_at FROM users
WHERE organization_id = 5 AND status = 'active';

-- Covering index: includes all columns the query touches
CREATE INDEX idx_users_covering
  ON users (organization_id, status, email, created_at);

-- EXPLAIN will show: "Using index" → pure index scan, no row lookup

3.5 Indexing Anti-Patterns That Kill Performance

Index Killers — Queries That Invalidate Indexes

Function on indexed column: WHERE YEAR(created_at) = 2024 — MySQL cannot use the index on created_at. Fix: WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'

Leading wildcard: WHERE email LIKE '%@gmail.com' — index unusable. Fix: Full-text search, or reverse the string.

Implicit type conversion: WHERE user_id = '123' when user_id is INT — MySQL casts every row, destroying the index.

OR across columns: WHERE email = 'x' OR phone = 'y' — index merge is rarely efficient. Fix: UNION two indexed queries.

NOT IN / !=: Typically forces full scans. MySQL's optimizer rarely uses indexes for negation.

3.6 Index Costs: Write Amplification

Every index has a write cost. When you INSERT a row, MySQL must update every index on that table. When you UPDATE an indexed column, MySQL deletes the old index entry and inserts a new one. This is called write amplification.

Write Cost = (1 table write) + (N index B+Tree updates) where N = number of indexes

A table with 15 indexes on it will have 15x the write cost versus a table with 1 index. This is why high-throughput event/log tables should have minimal indexes — the write performance degradation is severe.

Senior Engineer Heuristics for Indexing

Index selectivity: High-cardinality columns (user_id, email, UUID) make for excellent index leading columns. Low-cardinality columns (status with 3 values, boolean) are poor leading columns — use them as trailing columns in composites.

Rule of thumb: An index is worth it if it eliminates >80% of rows. If status='active' matches 95% of rows, the optimizer may skip that index entirely and do a full scan (cheaper than random I/O for 95% of rows).

Monitor with: SELECT * FROM sys.schema_unused_indexes — remove indexes no query uses. Unused indexes still pay the write cost.

Joins, Subqueries & Query Patterns

SQL joins are more than syntax — they map to specific internal algorithms with very different performance profiles depending on table sizes, indexes, and data distribution.

4.1 Join Algorithms: What the Engine Actually Does

MySQL uses three join algorithms internally:

-- MySQL drives from the table with fewer matching rows (outer)
-- to the table where it can use an index (inner)

-- Efficient: users has index on id, small result set from orders
SELECT u.email, o.total
FROM orders o
JOIN users u ON u.id = o.user_id
WHERE o.status = 'pending'
  AND o.created_at > '2024-01-01';

  where: {
    status: 'pending',

  // Prisma generates: SELECT + JOIN with index on user_id
});

4.2 JOIN Types and Their Semantics

-- INNER JOIN: Only rows with match in BOTH tables
SELECT u.id, p.title
FROM users u
INNER JOIN posts p ON p.author_id = u.id;
-- Users with no posts are EXCLUDED

-- LEFT JOIN: All rows from left, NULLs for non-matching right
SELECT u.id, COUNT(p.id) AS post_count
FROM users u
LEFT JOIN posts p ON p.author_id = u.id
GROUP BY u.id;
-- Users with 0 posts ARE included (count = 0)

-- Anti-join pattern: Find users with NO posts
SELECT u.id
FROM users u
LEFT JOIN posts p ON p.author_id = u.id
WHERE p.id IS NULL;
-- More efficient than: WHERE id NOT IN (SELECT author_id FROM posts)

4.3 Common Table Expressions (CTEs) and Window Functions

-- CTE for readable, reusable subquery
WITH active_orgs AS (
  SELECT id FROM organizations
  WHERE plan != 'free' AND created_at > '2023-01-01'
),
org_revenue AS (
  SELECT o.organization_id, SUM(p.amount) AS revenue
  FROM payments p
  JOIN active_orgs ao ON ao.id = p.organization_id
  GROUP BY o.organization_id
)
SELECT org.name, r.revenue,
       RANK() OVER (ORDER BY r.revenue DESC) AS revenue_rank
FROM org_revenue r
JOIN organizations org ON org.id = r.organization_id
ORDER BY revenue_rank;
Senior Engineer: Window Functions vs GROUP BY

Window functions (RANK, ROW_NUMBER, LAG, LEAD, SUM OVER) do NOT reduce rows like GROUP BY. They add computed columns based on a "window" of rows. They're essential for: leaderboards, running totals, YoY comparisons, finding the most recent record per group without subqueries.

Transactions & ACID Properties

Transactions are the correctness guarantee that separates databases from file systems. Mastering transactions means understanding both their power and their hidden performance costs.

5.1 ACID: Deep Theory

5.2 Transactions in Node.js + Prisma

// Pattern 1: Interactive transaction (sequential, single DB session)
const result = await prisma.$transaction(async (tx) => {
  // All operations share the same DB connection and transaction
  const account = await tx.account.findUnique({
    where: { id: fromAccountId },
    select: { balance: true }
  });

  if (account.balance < amount) {
    throw new Error('Insufficient funds'); // auto-rollback
  }

  const [debit, credit] = await Promise.all([
    tx.account.update({
      where: { id: fromAccountId },
      data: { balance: { decrement: amount } }
    }),
    tx.account.update({
      where: { id: toAccountId },
      data: { balance: { increment: amount } }
    }),
  ]);

  await tx.transferLog.create({
    data: { fromAccountId, toAccountId, amount, status: 'completed' }
  });

  return { debit, credit };
});

// Pattern 2: Batch transaction (optimized, fewer round trips)
const [updatedUser, newPost] = await prisma.$transaction([
  prisma.user.update({ where: { id: userId }, data: { postCount: { increment: 1 } } }),
  prisma.post.create({ data: { title, content, authorId: userId } }),
]);
// Both succeed or both fail — atomicity guaranteed
Transaction Anti-Patterns That Cause Production Incidents

Long-running transactions: A transaction that runs for 30 seconds holds locks, blocks other writers, fills the undo log, and causes "lock wait timeout exceeded" errors across your app. Always keep transactions short.

HTTP calls inside transactions: NEVER do this. If your external API call takes 5s or times out, your transaction is open for 5s+ holding database locks. Pattern: do the DB work in a transaction, THEN make external calls after commit.

Missing rollback handling: In Prisma's interactive transaction, any unhandled exception automatically rolls back. But in raw SQL, you must explicitly ROLLBACK on error — forgetting this leaves transactions open until connection timeout.

5.3 Transaction Isolation Levels

Isolation is a spectrum — higher isolation = more correctness but more contention. MySQL InnoDB defaults to REPEATABLE READ. Each level prevents different anomalies:

LevelDirty ReadNon-Repeatable ReadPhantom ReadUse When
READ UNCOMMITTEDPossiblePossiblePossibleAlmost never — only analytics approximations
READ COMMITTEDPreventedPossiblePossiblePostgreSQL default; good for most OLTP
REPEATABLE READPreventedPreventedPrevented*MySQL default; consistent reads
SERIALIZABLEPreventedPreventedPreventedFinancial systems requiring full serializability

*InnoDB's REPEATABLE READ prevents phantom reads via MVCC for snapshot reads, but NOT for current reads (SELECT ... FOR UPDATE).

Chapter 6

Query Optimization & EXPLAIN Plans

Reading EXPLAIN output is a core skill. It's the diagnostic tool that tells you exactly what the optimizer decided to do — and where to intervene.

6.1 How MySQL's Query Optimizer Works

When you run a SQL query, MySQL's optimizer (the "planner") doesn't execute it immediately. It generates multiple candidate execution plans, estimates the cost of each using table/index statistics, and picks the cheapest one. This is called cost-based optimization.

The optimizer considers: available indexes, table row counts, column cardinality statistics (updated by ANALYZE TABLE), join order permutations, and whether to use a filesort vs index sort.

6.2 Reading EXPLAIN: A Field Manual

EXPLAIN SELECT u.email, COUNT(o.id) AS order_count
FROM users u
JOIN orders o ON o.user_id = u.id
WHERE u.organization_id = 5
  AND o.status = 'completed'
GROUP BY u.id;

-- EXPLAIN output columns to focus on:
-- id: Step in query plan (subqueries have different ids)
-- select_type: SIMPLE, PRIMARY, SUBQUERY, DERIVED
-- table: Which table being accessed
-- type: Access method (THE MOST IMPORTANT COLUMN)
-- possible_keys: Indexes the optimizer considered
-- key: Index actually chosen (NULL = full table scan)
-- key_len: Bytes of index used (longer = more index columns used)
-- rows: Estimated rows examined (HUGE number = problem)
-- filtered: % of rows passing WHERE after index scan
-- Extra: Critical info — "Using filesort", "Using temporary", "Using index"
The `type` Column — From Best to Worst

Real Production EXPLAIN Analysis Workflow

1. Run EXPLAIN FORMAT=JSON SELECT ... for detailed cost information

2. Look for type: ALL on large tables → immediate index candidate

3. Look for Extra: Using filesort → query is sorting in memory/disk, not by index. Can we add the ORDER BY column to the index?

4. Look for Extra: Using temporary → GROUP BY or DISTINCT creating temp table. Expensive for large result sets.

5. Check rows — if it shows 5,000,000 for a query returning 10 rows, your index is wrong or missing.

6. Use EXPLAIN ANALYZE (MySQL 8.0.18+) to see ACTUAL row counts vs estimates — great for catching stale statistics.

6.3 Query Optimization Patterns

-- ❌ SLOW: ORDER BY on unindexed column after large scan
SELECT * FROM posts
WHERE organization_id = 5
ORDER BY view_count DESC
LIMIT 10;

-- ✅ FIX: Composite index covering both WHERE and ORDER BY
CREATE INDEX idx_posts_org_views ON posts (organization_id, view_count DESC);

-- ❌ SLOW: COUNT(*) on large table with no filter
SELECT COUNT(*) FROM events;

-- ✅ FIX: Use information_schema for approximate counts
SELECT TABLE_ROWS FROM information_schema.TABLES
WHERE TABLE_NAME = 'events';

Chapter 7

Pagination Strategies

Pagination seems trivial until you hit page 10,000 and your UI takes 30 seconds to load. There are three fundamentally different strategies — each with distinct performance profiles.

7.1 OFFSET Pagination — The Dangerous Default

-- Classic offset pagination
SELECT * FROM posts WHERE org_id = 5
ORDER BY created_at DESC
LIMIT 20 OFFSET 10000;  -- Page 500

-- MySQL must SCAN 10,020 rows to return 20!
-- Cost grows linearly: OFFSET 1M = scan 1M rows, discard 999,980
OFFSET Pagination is O(N) — It Does Not Scale

At page 1: scan 20 rows. At page 500: scan 10,020 rows. At page 10,000: scan 200,020 rows. The deeper the page, the more expensive the query. For user-facing APIs with large datasets, this is a latency time bomb.

7.2 Cursor-Based (Keyset) Pagination — The Production Standard

// Keyset pagination using the last seen row's values as cursor
// First page:
SELECT id, title, created_at FROM posts
WHERE org_id = 5
ORDER BY created_at DESC, id DESC   -- id as tiebreaker
LIMIT 20;

-- Next page: use last row's values as the cursor
SELECT id, title, created_at FROM posts
WHERE org_id = 5
  AND (created_at < '2024-06-15 10:30:00'
       OR (created_at = '2024-06-15 10:30:00' AND id < 4521))
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- In Prisma:
const posts = await prisma.post.findMany({
  where: { orgId: 5 },
  orderBy: [{ createdAt: 'desc' }, { id: 'desc' }],
  cursor: cursor ? { id: cursor } : undefined,
  skip: cursor ? 1 : 0,  // skip the cursor row itself
  take: 20,
});
const nextCursor = posts.length === 20 ? posts[19].id : null;

Replication, Partitioning & Sharding

These are the three scaling axes of any database system. Understanding when and how to use each determines whether your system survives 10x growth.

8.1 MySQL Replication

Replication creates copies of data across multiple MySQL servers. The primary handles all writes; replicas receive a stream of changes and serve reads. This is the first scaling step every SaaS takes.

Handling Replication Lag in Application Code
// Pattern: Write to primary, read from replica with fallback
const primaryPrisma = new PrismaClient({ datasourceUrl: PRIMARY_URL });
const replicaPrisma = new PrismaClient({ datasourceUrl: REPLICA_URL });

async function createPostAndReturn(data) {
  // Write to primary
  const post = await primaryPrisma.post.create({ data });

  // Read your own write: route back to primary for immediate consistency
  // OR: wait for replica (unreliable), OR: return the data we just created
  return post;  // Don't read from replica immediately after write
}

Sharding distributes data across multiple independent database servers. Each server owns a subset of the data (a "shard"). Unlike replication (all replicas have all data), with sharding each server has only its portion.

// Cache-Aside Pattern in Node.js
async function getUser(userId) {
  const cacheKey = `user:${userId}`;

  // 1. Try cache first
  const cached = await redis.get(cacheKey);
  if (cached) return JSON.parse(cached);

  // 2. Cache miss: load from DB
  const user = await prisma.user.findUnique({ where: { id: userId } });
  if (!user) return null;

  // 3. Populate cache with TTL
  await redis.setex(cacheKey, 300, JSON.stringify(user)); // 5 min TTL

  return user;
}

// Cache invalidation on update
async function updateUser(userId, data) {

}
Cache Stampede: The Silent Production Killer

When a popular cache key expires, hundreds of concurrent requests simultaneously miss the cache, all hit the DB simultaneously, and overwhelm it. This is the "thundering herd" or cache stampede problem.

Fix 1 — Probabilistic early expiry: Before TTL expires, with some probability, refresh the cache early. Prevents simultaneous expiry.

Fix 2 — Mutex/lock on cache miss: On miss, acquire a distributed lock. Only one process fetches from DB and populates cache; others wait and then read from cache.

Fix 3 — Background refresh: Serve stale data while async background job refreshes the cache. Excellent for non-critical freshness requirements.

10.1 Why Database Connections Are Expensive

A database connection is not a cheap object. Establishing a TCP connection + MySQL handshake + authentication + session state setup costs 20-50ms and consumes server-side resources (memory, file descriptors, thread context). MySQL has a hard limit on simultaneous connections (default: 151).

11.2 Deadlock: The Classic Case

-- Transaction A                    -- Transaction B
BEGIN;                             BEGIN;
UPDATE accounts                    UPDATE accounts
  SET balance = balance - 100        SET balance = balance - 200
  WHERE id = 1;  -- LOCKS row 1       WHERE id = 2;  -- LOCKS row 2

UPDATE accounts                    UPDATE accounts
  SET balance = balance + 100        SET balance = balance + 200
  WHERE id = 2;  -- WAITS for B      WHERE id = 1;  -- WAITS for A

-- DEADLOCK DETECTED: InnoDB kills one transaction (victim)
-- ERROR 1213: Deadlock found when trying to get lock; try restarting transaction
Deadlock Prevention Strategies
1
Consistent Lock Ordering
Always acquire locks in the same order. If all transactions lock account 1 before account 2, deadlocks on this pattern are impossible. Sort IDs before accessing: const [low, high] = [id1, id2].sort()
2
Short Transactions
The less time locks are held, the less chance of deadlock. Do all SELECT/computation outside the transaction, enter the transaction only for the writes.
3
Retry on Deadlock
Deadlocks are a normal part of concurrent database systems. Always wrap transactions in retry logic with exponential backoff. InnoDB gives error code 1213.
4
SELECT ... FOR UPDATE
When you need to read and then modify data in the same transaction, use SELECT ... FOR UPDATE to acquire an exclusive lock on read. This prevents another transaction from modifying the row between your read and write.
// Retry wrapper for deadlock-prone transactions
async function withDeadlockRetry(fn, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    try {
      return await fn();
    } catch (error) {
      const isDeadlock = error.code === 'P2034'  // Prisma deadlock code
        || error.message.includes('Deadlock');

      if (!isDeadlock || attempt === maxRetries - 1) throw error;

      const delay = Math.pow(2, attempt) * 100; // 100ms, 200ms, 400ms
      await new Promise(r => setTimeout(r, delay));
    }
  }
}

13.1 The N+1 Problem: Diagnosis and Fix

The N+1 problem occurs when you fetch N records, then issue 1 additional query per record. The name comes from: 1 query to get the list + N queries to get related data = N+1 total queries.

    where: { id: post.authorId }

}
// 100 more queries: SELECT * FROM users WHERE id = ?
// Total: 101 queries for 100 posts

// ✅ FIX: Use include to let Prisma batch the join
const posts = await prisma.post.findMany({

    author: { select: { id: true, email: true, name: true } }

});
// 2 queries: SELECT posts + SELECT users WHERE id IN (1,2,3,...)
// Or 1 JOIN query depending on Prisma's strategy

14.2 The p50/p95/p99 Mental Model

Never look at average latency. Average hides the worst-case user experience. Always profile percentiles:

  • p50 (median): 50% of requests finish under this time — "typical" user
  • p95: 95% finish under this — "95th percentile user" — your SLA-relevant metric
  • p99: 99% finish under this — catches outliers, long-running queries, lock waits

Mental Model: Optimize for p99, Not Average

If your p50 latency is 50ms but your p99 is 5 seconds, 1% of users (potentially thousands per day at scale) experience a broken product. High p99 is caused by: lock waits, connection pool exhaustion, garbage collection pauses, cold cache misses, or outlier query parameters hitting expensive code paths.

async function checkRateLimit(userId, maxRequests, windowSeconds) {
  const key = `ratelimit:${userId}:${Math.floor(Date.now() / 1000 / windowSeconds)}`

  // Lua script for atomic check-and-increment
  const script = `
    local count = redis.call('INCR', KEYS[1])
    if count == 1 then
      redis.call('EXPIRE', KEYS[1], ARGV[1])
    end
    return count
  `
  const count = await redis.eval(script, 1, key, windowSeconds)
  return { allowed: count <= maxRequests, count, maxRequests }
}

// Pattern 3: Cache-aside with stampede protection (mutex lock)
async function getCachedOrFetch(key, ttl, fetchFn) {
  const cached = await redis.get(key)
  if (cached) return JSON.parse(cached)

  const lockKey = `lock:${key}`
  const lockAcquired = await redis.set(lockKey, '1', 'NX', 'EX', 10)

  if (lockAcquired) {
    try {
      const data = await fetchFn()
      await redis.setex(key, ttl, JSON.stringify(data))
      return data
    } finally {
      await redis.del(lockKey)
    }
  } else {
    // Another process is fetching — wait briefly and retry
    await new Promise(r => setTimeout(r, 50))
    return getCachedOrFetch(key, ttl, fetchFn)
  }
}

Queues decouple producers from consumers, enabling asynchronous processing, load leveling, and resilience to downstream failures. They're a fundamental building block of scalable backends.

16.1 Why Queues?

Synchronous request-response works only when the consumer is faster than the producer and always available. Queues allow you to:

  • Absorb traffic spikes: 1000 req/s can queue up and be processed at 100 req/s sustainably
  • Decouple services: Email service down? Messages queue, delivered when service recovers
  • Retry on failure: Failed message returns to queue for retry with backoff

B-Trees vs. LSM Trees

The two dominant data structures for database storage. B-Trees optimize reads; LSM Trees optimize writes. This tradeoff defines entire database categories.

19.1 B+Tree: The Read-Optimized Structure

B+Trees are the foundation of MySQL InnoDB, PostgreSQL, and most traditional RDBMS. The structure is:

  • Balanced tree: All leaf nodes are at the same depth — every lookup takes O(log N) I/Os
  • High branching factor: Each node holds hundreds of keys (not binary like BST) — for 16KB pages with 4-byte keys, a node holds ~4000 entries. Billion rows = 3-4 levels
  • Leaf nodes linked: Leaf pages form a doubly linked list — enables efficient range scans without traversing back up the tree
  • In-place updates: Modified rows update existing pages — good for read performance, but updates cause random writes ("write amplification" for HDDs)

19.2 LSM Tree: The Write-Optimized Structure

Log-Structured Merge Trees power Cassandra, RocksDB, LevelDB, ScyllaDB, and ClickHouse. The core insight: sequential writes are orders of magnitude faster than random writes (especially on spinning disks and for SSDs which have write amplification from garbage collection).

Chapter 20

Write-Ahead Logging (WAL)

WAL is the mechanism that makes databases durable. Without WAL, a server crash mid-transaction would corrupt your data forever.

20.1 The WAL Protocol

The fundamental rule: log entries must be written to durable storage before the data pages they describe are modified. This means if the server crashes, the database can replay the log to reconstruct any partial changes, then roll back any uncommitted transactions.

1
Transaction Begins
InnoDB assigns a transaction ID (TRX_ID). The transaction begins modifying data in the buffer pool (memory only).
2
Write to Redo Log (WAL)
Every change is written to the redo log buffer in memory as a "redo log record" describing the physical change (page X, offset Y, old value, new value).
3
Commit: fsync the Redo Log
When COMMIT is issued, InnoDB calls fsync() to flush the redo log to disk. This is the durability guarantee — the transaction survives after this point. This is why commit latency is tied to disk write speed.
4
Background Flush to Data Files
Dirty pages in the buffer pool are asynchronously flushed to .ibd data files by background threads. This is NOT on the critical commit path.
5
Crash Recovery
On restart after crash: InnoDB replays the redo log (re-applies all committed changes to data pages), then uses the undo log to roll back any uncommitted transactions. Database is returned to a consistent state.
The innodb_flush_log_at_trx_commit Setting

Value 1 (default, full ACID): fsync on every commit. Maximum durability. Maximum latency (~1-5ms per commit on spinning disk). Required for banking, payment systems.

Value 2 (high performance, slight risk): Write to OS buffer on commit, fsync every 1 second. Lose up to 1 second of committed transactions on OS crash (not DB crash). 5-10x faster writes.

Value 0 (maximum performance, dangerous): Write and flush every 1 second only. Lose up to 1 second on MySQL crash. Not recommended for production.

Chapter 21

MVCC: Multi-Version Concurrency Control

MVCC is how InnoDB achieves high concurrency without readers blocking writers. It's the mechanism behind consistent snapshots and isolation levels.

21.1 MVCC Fundamentals

Without MVCC, a read transaction would need to lock all rows it reads to prevent modifications — readers would block writers and vice versa. MVCC solves this by keeping multiple versions of each row. Readers see a consistent snapshot of the database as of their transaction start time, without blocking writers.

MVCC Row Version Chain Current Row: [TRX_ID: 500 | data: "Alice" | DB_ROLL_PTR → undo log] │ ▼ Undo Log: [TRX_ID: 300 | data: "Alicia" | ROLL_PTR → undo log] │ ▼ [TRX_ID: 100 | data: "Ali" | ROLL_PTR → NULL] Transaction with snapshot_trx_id = 350: - Sees current row? TRX_ID 500 > 350 → NO (committed after my snapshot) - Checks undo: TRX_ID 300 < 350 → YES → reads "Alicia" Readers see "Alicia" while writers update to "Alice" — no lock conflict

21.2 Read Views: The Snapshot Mechanism

When a transaction starts a read (in REPEATABLE READ isolation), InnoDB creates a "Read View" containing:

  • The current transaction ID
  • The list of all active (uncommitted) transaction IDs at this moment
  • The minimum active transaction ID (low water mark)
  • The next transaction ID to be assigned (high water mark)

Any row version created by a transaction in the active list, or with TRX_ID above the high water mark, is invisible to this read view. The engine walks the undo log chain until it finds a visible version.

Why Long-Running Transactions Are Dangerous (MVCC Angle)

Every row modified after your transaction started must keep its old version in the undo log until your transaction commits or rolls back (because you might need to read the old version). A transaction open for 1 hour means 1 hour of undo log accumulation for every modified row in the system. This causes: undo log growth (disk space), version chain traversal slowdown (reads get slower as chains lengthen), and eventual "undo log full" errors.

22.1 The Anomalies — What Each Level Prevents

Dirty Read (READ UNCOMMITTED only)

-- T=2: Tx A reads balance = 0 (dirty read)
-- T=3: Tx B rolls back. Balance is back to 100.
-- T=4: Tx A made a decision based on non-existent data

-- T=1: Tx A: SELECT COUNT(*) FROM orders WHERE user_id=5 → 3

-- But for SELECT ... FOR UPDATE, InnoDB uses gap locks to prevent phantoms

Chapter 25

CAP Theorem & Consistency Models

The most misunderstood theorem in distributed systems. Most engineers know the acronym but can't explain the practical engineering implications.

25.1 CAP Theorem — Precise Definition

The CAP Theorem states: a distributed system can provide at most two of these three guarantees simultaneously:

PropertyDefinitionWhat "violated" looks like
Consistency (C)Every read receives the most recent write or an error (linearizability)Reading stale data — "I just wrote X but the read returned old value"
Availability (A)Every request receives a non-error response (may be stale)Service returns 503 / "service unavailable" during partition
Partition Tolerance (P)System continues despite network partitions (message loss between nodes)Not applicable — network partitions WILL happen in any distributed system
The Real Insight: P is Not Optional

Network partitions are not hypothetical — they happen with non-zero probability in any multi-node system. Therefore, you MUST design for P. The real choice is: when a partition occurs, do you sacrifice C (allow stale reads, maintain availability) or A (return errors until partition heals, maintain consistency)?

This makes CAP a CP vs AP choice in the face of partitions. Normal operations (no partition): you can have both C and A.

25.3 PACELC: The More Complete Model

CAP only considers partitioned state. PACELC extends it: "If there's a Partition → tradeoff A vs C. Else (normal operation) → tradeoff L (Latency) vs C (Consistency)."

Example: Even without a partition, returning a linearizable read from a multi-region database requires waiting for cross-region coordination — adding hundreds of milliseconds of latency. You can avoid this by serving from a local replica (lower consistency, lower latency).

Raft & Paxos: Distributed Consensus

Consensus algorithms enable a cluster of nodes to agree on a single value despite failures. They're the foundation of distributed databases, Kubernetes, Kafka, and cloud coordination services.

26.1 The Problem: What Is Consensus?

In a distributed system with N nodes, consensus means: given a proposed value (a log entry, a leader, a configuration change), all non-faulty nodes agree on the same value, and that agreement is permanent once made.

Without consensus: each node could make independent decisions that diverge — "split brain" — resulting in data corruption or inconsistency.

26.2 Raft: The Understandable Consensus Protocol

Raft was designed explicitly to be understandable (vs. Paxos, which is notoriously difficult to reason about). Raft decomposes consensus into three sub-problems:

1
Leader Election
Nodes start as Followers. If a Follower doesn't receive a heartbeat from a Leader within an election timeout (150-300ms randomized), it becomes a Candidate and requests votes. A Candidate becomes Leader if it receives majority votes (⌊N/2⌋ + 1). Leaders send periodic heartbeats to prevent new elections.
2
Log Replication
All writes go to the Leader. Leader appends to its log, sends AppendEntries RPC to all Followers. Once a majority acknowledges, the entry is "committed" and applied to the state machine. Leader notifies Followers of the commit index.
3
Safety (Log Consistency)
A node with an incomplete log cannot become Leader (it won't receive votes from nodes with more up-to-date logs). This guarantees committed entries are never lost — the Leader always has all committed entries.

Chapter 29

Distributed Transactions & The Saga Pattern

When a business operation spans multiple services with independent databases, maintaining ACID guarantees requires careful pattern selection. Distributed transactions are the hardest problem in microservices.

29.1 Why 2PC (Two-Phase Commit) Usually Fails

2PC is the classic distributed transaction protocol: Phase 1 (Prepare) — coordinator asks all participants to prepare and lock resources. Phase 2 (Commit) — if all prepared, coordinator tells all to commit.

Problems: The coordinator is a single point of failure. If it crashes between phases, participants are left holding locks indefinitely (blocking). Network partitions cause the same blockage. In practice, 2PC destroys availability and throughput.

29.2 The Saga Pattern: Eventual Consistency Without 2PC

A Saga decomposes a distributed transaction into a sequence of local transactions, each publishing an event that triggers the next step. If any step fails, compensating transactions are executed to undo completed steps.

Order Processing Saga (Choreography) 1. OrderService: CREATE order (status=PENDING) │ → publish: OrderCreated ▼ 2. InventoryService: RESERVE items │ → publish: InventoryReserved OR: publish: InventoryFailed → compensate: CANCEL order ▼ 3. PaymentService: CHARGE customer │ → publish: PaymentSucceeded OR: publish: PaymentFailed → compensate: RELEASE inventory + CANCEL order ▼ 4. OrderService: UPDATE order (status=CONFIRMED) │ → publish: OrderConfirmed ▼ 5. NotificationService: SEND confirmation email Each step is a local transaction → no distributed locks Eventual consistency: system converges to correct state via compensation 
// Saga step with compensation in Node.js
class OrderSaga {
  async execute(orderData) {
    const saga = []

    try {
      // Step 1: Create order
      const order = await orderService.create(orderData)
      saga.push({ compensate: () => orderService.cancel(order.id) })

      // Step 2: Reserve inventory
      await inventoryService.reserve(order.items)
      saga.push({ compensate: () => inventoryService.release(order.items) })

      // Step 3: Charge payment
      const charge = await paymentService.charge(order.userId, order.total)
      saga.push({ compensate: () => paymentService.refund(charge.id) })

      // Step 4: Confirm order
      await orderService.confirm(order.id)

      return order

    } catch (error) {
      // Execute compensating transactions in reverse order
      for (const step of saga.reverse()) {
        try { await step.compensate() }
        catch (e) { /* log compensation failure — needs manual intervention */ }
      }
      throw error
    }
  }
}

// Token bucket rate limiter with Redis (production-grade)
const tokenBucketScript = `
  local key = KEYS[1]
  local capacity = tonumber(ARGV[1])
  local refill_rate = tonumber(ARGV[2])  -- tokens per second
  local now = tonumber(ARGV[3])          -- current timestamp (ms)
  local requested = tonumber(ARGV[4])    -- tokens for this request

  local bucket = redis.call('HMGET', key, 'tokens', 'last_refill')
  local tokens = tonumber(bucket[1]) or capacity
  local last_refill = tonumber(bucket[2]) or now

  -- Refill tokens based on time elapsed
  local elapsed = (now - last_refill) / 1000
  tokens = math.min(capacity, tokens + elapsed * refill_rate)

  local allowed = tokens >= requested
  if allowed then tokens = tokens - requested end

  redis.call('HMSET', key, 'tokens', tokens, 'last_refill', now)
  redis.call('EXPIRE', key, 3600)

  return { allowed and 1 or 0, math.floor(tokens) }
`

async function tokenBucketLimit(userId, capacity = 100, refillRate = 10) {
  const key = `bucket:${userId}`
  const [allowed, remaining] = await redis.eval(
    tokenBucketScript, 1, key, capacity, refillRate, Date.now(), 1
  )
  return { allowed: Boolean(allowed), remaining }
}

  next()
})

The circuit breaker prevents cascading failures: when a downstream service is failing, stop sending requests to it instead of causing your service to fail too. Three states: Closed (normal), Open (failing, reject requests), Half-Open (test if recovered).

Retry with Exponential Backoff and Jitter
async function withRetry(fn, options = {}) {
  const { maxAttempts = 3, baseDelay = 1000, maxDelay = 30000 } = options

  for (let attempt = 1; attempt <= maxAttempts; attempt++) {
    try {
      return await fn()
    } catch (error) {
      if (attempt === maxAttempts || !isRetryable(error)) throw error

      // Exponential backoff with full jitter (avoids thundering herd)
      const exponential = Math.min(maxDelay, baseDelay * Math.pow(2, attempt - 1))
      const delay = Math.random() * exponential  // jitter: 0 to exponential
      await new Promise(r => setTimeout(r, delay))
    }
  }
}

function isRetryable(error) {
  // Retry on network errors and 429/503, not on 400/401/404
  return error.code === 'ECONNRESET'
    || error.status === 429
    || error.status === 503
}

Production Incident Response

How you handle a production incident defines your reputation as an engineer. The best engineers are calm, methodical, and communicative — not heroic cowboys.

34.1 The Incident Response Framework

1
Detect & Acknowledge (T+0 to T+5 minutes)
Alert fires. Acknowledge it. Open incident channel (Slack #incident). Declare severity (S1=total outage, S2=major feature down, S3=degraded). Assign incident commander. Communicate to stakeholders: "We're aware and investigating."
2
Assess Scope (T+5 to T+15 minutes)
What's broken? What's working? How many users affected? What changed recently? (Deployments in last 2 hours? Config changes? Traffic spike?) Check dashboards: error rate, latency, DB metrics, infra metrics.
3
Mitigate First, Diagnose Second
Restore service as fast as possible. Can you roll back the last deployment? Can you disable the breaking feature flag? Can you restart the failing service? Don't wait for root cause — mitigate first, investigate why later.
4
Root Cause Investigation
After mitigation: look at logs, traces, metrics. Build a timeline. What is the causal chain? "Deployment at 14:32 → increased DB queries → pool exhaustion at 14:38 → API timeouts at 14:40 → alerts at 14:41."
5
Post-Mortem (Blameless)
Write a detailed post-mortem within 48 hours: timeline, root cause, impact, resolution, action items. Blameless — systems fail, not people. Action items must be assigned with owners and deadlines.

34.2 Database Incident Playbooks

Incident: "All API requests timing out"

T+0: Alert: API p99 latency > 30s. Check: SHOW PROCESSLIST — hundreds of queries in "Waiting for lock" state.

T+2: Identify the blocker: SELECT * FROM information_schema.INNODB_TRX ORDER BY trx_started\G — one long-running transaction from 20 minutes ago holding a row lock.

T+3: Kill the blocking transaction: KILL QUERY [pid]. All waiting queries instantly unblock.

T+5: Service recovers. Root cause: a batch job opened a transaction, hit an exception in the application code, and never committed or rolled back. The connection held the lock until timeout (8 hours default).

Fix: Wrap all batch operations in proper try/catch/rollback. Set interactive_timeout and wait_timeout to 60s. Add monitoring for long-running transactions: alert if any transaction > 60s.

Incident: "Database connection pool exhausted"

Symptoms: Error: "All connections in pool are used", API returns 503.

Diagnosis: Each new deployment creates a new PrismaClient (new pool). 20 pods × 10 connections = 200, but MySQL max_connections = 151. Connection refused.

Immediate fix: Reduce pool size per pod to 5 (100 total) or scale down pods. Long-term: add ProxySQL, ensure PrismaClient singleton pattern, set MySQL max_connections = 500.

36.2 Case Study: Debugging a Production Performance Crisis

Scenario: API latency spikes every day at 9am. p99 goes from 200ms to 8s. Resolves by 10am. Not a deployment issue (no deploys happen at 9am).

1
Hypothesis: Traffic spike
Check QPS graph at 9am. QPS is 2x normal. Business users in Eastern timezone start their day. Hypothesis partially confirmed but doesn't fully explain 40x latency increase from 2x traffic.
2
Database investigation
Check DB slow query log. At 9am: a scheduled daily report job runs. It does a full table scan on a 50M row events table. This query takes 45 seconds and locks shared resources, competing with production API queries for connection pool slots.
3
Fix
Move report job to read replica. Add index on events table for the report query. Schedule report to run at 3am (off-peak). Add query timeout on report connection (60 seconds max). Result: 9am latency spike eliminated.

36.3 Mental Models for Production Engineers

Mental Model 1: Measure Before Optimizing

Donald Knuth: "Premature optimization is the root of all evil." Before adding Redis caching, indexes, or replication, measure: Is this actually slow? By how much? What's the bottleneck? Optimize the bottleneck, not what you assume is slow.

Mental Model 2: The Reliability Stack

System reliability = product of component reliabilities. If you have 3 services each with 99.9% uptime: 0.999 × 0.999 × 0.999 = 99.7%. More components = lower system reliability. Minimize the critical path. Design so failures in non-critical components degrade gracefully, not catastrophically.

Mental Model 3: Design for Observability First

Before writing a single line of a new service, decide: what metrics will tell you it's healthy? What logs will help you debug failures? What traces will show you where latency comes from? Systems without observability are black boxes you can't debug in production.

Mental Model 4: Failure is Normal — Design for It

Any external service call WILL eventually fail. Any disk WILL eventually fail. Any network connection WILL eventually timeout. Design your system assuming each component will fail, and ensure failures are isolated, retried, and don't cascade. The question isn't "will this fail?" but "when it fails, what happens?"

Mental Model 5: Read the Fundamentals, Not Just the Framework Docs

Frameworks come and go. The fundamentals — ACID, MVCC, B+Trees, CAP theorem, distributed consensus, network partitions — apply across every system you'll ever build. Staff engineers invest in fundamentals because they transfer across decades of technology change. Framework-only knowledge expires every 3-5 years.

The Staff Engineer Mindset Checklist

When reviewing any system or design, ask:

✓ Correctness: Under concurrent load, does this produce correct results? Are there race conditions?

✓ Scalability: Which component breaks first as load increases 10x? 100x?

✓ Operability: If this fails at 3am, can the on-call engineer diagnose it in 15 minutes?

✓ Reliability: What's the blast radius of each failure mode? Can we reduce it?

✓ Cost: What's the infrastructure cost at 10x current scale? Is this the cost-efficient choice?

✓ Security: What's the attack surface? Are secrets handled correctly? Is data encrypted at rest and in transit?

✓ Maintainability: Can a new team member understand and modify this in 6 months?

Conclusion: Mastery in backend engineering is not about knowing every technology — it's about deeply understanding fundamentals, making principled tradeoffs, and being able to reason about systems you haven't seen before. Every framework, database, and cloud service you'll encounter in your career is built on the concepts in this guide: consensus, durability, isolation, distributed coordination, and observability. Invest in the fundamentals, and the rest becomes pattern recognition.

The goal is not to memorize answers — it is to develop the mental models that let you derive answers to problems you've never seen before. That's what distinguishes a principal engineer from a senior engineer: not more knowledge, but better reasoning.
